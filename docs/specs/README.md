# 스펙

기획(Claude Code)이 작성하고 구현(Codex)이 받아가는 작업 명세입니다.

## 목록

| 번호 | 제목 | 상태 |
|---|---|---|
| [01](01-promote-to-site-root.md) | 새 포트폴리오를 실제 사이트로 승격 | 구현 대기 |

## 작성 규칙

스펙 하나는 **한 번에 끝낼 수 있는 크기**로 자릅니다. 여러 관심사가 섞이면
문제가 생겼을 때 원인을 좁히지 못합니다.

각 스펙에 반드시 들어가는 것:

- **목적** — 왜 하는지. 무엇을 하는지보다 먼저.
- **현재 상태** — 손대기 전 구조. 구현자가 저장소를 뒤지지 않아도 되게.
- **작업** — 파일·줄 번호까지 특정. 조사는 기획이 미리 해둔다.
- **제약** — 하지 말아야 할 것과 그 이유.
- **완료 조건** — 체크리스트. 실제로 확인 가능한 항목만.
- **다루지 않는 것** — 범위가 번지는 걸 막는다.

## 진행 방식

1. 기획이 `worktree-portfolio-ui-polish` 브랜치에 스펙을 커밋한다
2. 구현이 `codex-impl` 브랜치에서 `git merge worktree-portfolio-ui-polish`로 당겨간다
3. 구현이 완료 조건을 직접 확인한 뒤 커밋·푸시한다
4. 기획이 결과를 보고 다음 스펙을 쓰거나 수정을 요청한다

기획은 코드를 건드리지 않고 `docs/` 아래만 수정합니다. 그래서 두 브랜치가
같은 파일을 만질 일이 없고 충돌이 나지 않습니다.

스펙이 애매하면 구현자는 추측하지 말고 되물어야 합니다.
확정받는 쪽이 다시 만드는 것보다 쌉니다.
